JWT: Secure and Scalable Authentication

by Ricardo Cruz

OutSystems

HTTP is stateless by design — every request stands alone, with no memory of what came before[cite: 1, 2]. So how does a web app know it's still you on the next click? This is the problem authentication tokens solve, and it's why JSON Web Tokens (JWTs) have become the default choice for modern APIs and microservices[cite: 1, 2]. The concepts below apply to any stack, and the practical examples are shown in OutSystems[cite: 1, 2].

Authorization & the stateless web

A static web site just serves pages: request a URL, get a page back, no identity involved[cite: 1, 2]. The moment an app needs to know who is asking — to show a personalized dashboard, restrict administrative actions, or fetch sensitive account details — the server needs a way to recognize the same user across multiple requests[cite: 1, 2].

Authorization ensures that a user is permitted to access the resource or operation they are requesting[cite: 2]. Since the HTTP protocol keeps no memory between requests, that identity payload must travel alongside each request[cite: 1, 2].

Session tokens vs JWTs

Historically, web applications relied on session tokens[cite: 1, 2]. On login, the server generates a random string, creates an active session entry in a server-side store (memory or database), and sends back a session_id cookie[cite: 1, 2]. For subsequent requests, the server looks up the session_id in its log/database to identify the user[cite: 1, 2].

While straightforward, session tokens face scalability bottlenecks when scaling horizontally across multi-server environments[cite: 1, 2]:

  • Load Balancer complexity: The load balancer must use "sticky sessions" to pin a client to a specific application server[cite: 2].
  • Centralized Session Store: Alternatively, servers share a centralized cache like Redis[cite: 2]. However, this shared cache becomes a single point of failure and adds latency to every single request lookup[cite: 2].

A JSON Web Token (JWT) flips this model: instead of storing identity on the server and passing a reference ID, the token carries the user state itself inside a self-contained, cryptographically signed container[cite: 1, 2]. Any backend server possessing the signing secret or public key can instantly verify the token's integrity without consulting a central database[cite: 1, 2].

Anatomy of a JWT

A JWT is a string consisting of three Base64URL-encoded segments joined by dots[cite: 1, 2]:

HEADER.PAYLOAD.SIGNATURE

1. Header

Specifies the metadata about the token, such as the hashing algorithm used (e.g., HS256 or RS256) and the token type[cite: 1, 2]:

{
  "alg": "HS256",
  "typ": "JWT"
}

2. Payload

Contains the claims — statements about the user and additional context[cite: 2]. Claims are divided into registered (standard), public, and custom claims[cite: 2]:

{
  "iss": "oauth-provider",
  "sub": "1234567890",
  "name": "John Doe",
  "email": "john.doe@email.com",
  "admin": true,
  "iat": 1516239022,
  "exp": 1516257022
}

Key claim attributes include iss (issuer), sub (subject/user ID), iat (issued at timestamp), and exp (expiration timestamp)[cite: 2].

3. Signature

The signature is calculated by combining the Base64URL-encoded header, the Base64URL-encoded payload, and a secret key using the specified algorithm[cite: 2]:

HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

Resulting signature snippet[cite: 2]:

KMUFsIDTnFmyG3nMiGM6H9FNFUROf3wh7SmqJp-QV30

Signature Validation Workflow

When a client presents a JWT in an Authorization: Bearer <token> header, the server validates it by taking the received header and payload, re-running the signing function f(header, payload, secret), and comparing the newly calculated hash against the signature attached to the token[cite: 2]. If they match, the token is genuine and hasn't been modified[cite: 2].

Crucial Distinction: Encoded vs. Encrypted
JWTs are encoded using Base64URL, not encrypted[cite: 2]! Anyone who intercepts the token can decode it in seconds using standard tools[cite: 2]. Never store sensitive credentials, passwords, or credit card numbers inside a JWT payload[cite: 2].

Advantages & Disadvantages

Advantages Disadvantages & Mitigations
Stateless Authentication: Eliminates server-side session lookup overhead[cite: 2]. Hard to Revoke: Once issued, a JWT is valid until it expires[cite: 2].
Mitigation: Use short-lived access tokens + refresh tokens[cite: 2].
High Scalability: Ideal for microservices, mobile apps, and multi-region APIs[cite: 2]. Security Risks (XSS & Theft): Malicious scripts can steal tokens from local storage[cite: 2].
Mitigation: Store in HttpOnly cookies and enforce CSP rules[cite: 2].
Cross-Domain / Cross-Platform: Works seamlessly across decoupled client applications[cite: 2]. Replay Attacks: Intercepted tokens can be replayed[cite: 2].
Mitigation: Force HTTPS, rotate tokens, and bind tokens to clients[cite: 2].
Built-in RBAC: User roles and permissions reside directly within the payload claims[cite: 2]. Token Size: Larger than opaque session IDs, increasing header overhead on every HTTP request[cite: 2].

Best Practices

  1. Keep Tokens Short-Lived: Set expiration times (exp) to minutes or hours rather than days to minimize the risk window of leaked tokens[cite: 2].
  2. Secure Storage: Prefer HttpOnly, Secure, and SameSite cookies over browser local storage to mitigate Cross-Site Scripting (XSS) attacks[cite: 2].
  3. Always Enforce HTTPS: Transport Layer Security prevents token interception over open networks[cite: 2].
  4. Server-Side Claim Validation: Always verify claims (issuer, audience, expiration) on every API request, and periodically rotate signing keys[cite: 2].

OutSystems Implementation & Usage

Implementing JWT authentication in OutSystems applications typically involves handling OIDC tokens on the client side and enforcing server-side action validation[cite: 2].

1. Client-Side Inspection

In modern OutSystems Reactive or Mobile apps using OpenID Connect (OIDC) or custom SSO providers (e.g., Okta, Azure AD), tokens are received and maintained in client storage[cite: 2]. Inspecting DevTools reveals items like[cite: 2]:

  • oidcAccessToken: The bearer JWT used for API authorization[cite: 2].
  • oidcIdToken: Encodes profile details about the authenticated user[cite: 2].
  • oidcRefreshToken: Used to request a fresh access token without requiring manual re-authentication[cite: 2].

2. Server Logic & Authorization Actions

When exposed REST APIs or Server Actions receive requests, custom verification flows (such as a JWT_GetInfo or JWT_ValidateUser wrapper) evaluate the incoming request headers[cite: 2]:

  • Validate token structure and cryptographic signature[cite: 2].
  • Extract user roles and identity claims (e.g., verifying if a user is an Admin, Logistics Provider, or Customer)[cite: 2].
  • If invalid or expired, abort execution immediately with an appropriate HTTP status code (401 Unauthorized or 500 Internal Error)[cite: 2].

3. The JWT_Core Forge Component

In OutSystems, standard Forge components like JWT_Core provide clean, reusable actions for token operations[cite: 2]:

  • Create Token: CreateSignedSymmetricToken, CreateSignedAsymmetricTokenWithPemKey, or CreateSignedAsymmetricTokenWithJsonWebKey[cite: 2].
  • Read & Validate: ReadAndValidateToken (checks signature, expiration, and claims) and ReadTokenWithoutValidation (for inspecting public header/payload claims)[cite: 2].

Closing thoughts

Session tokens and JWTs solve the same fundamental problem — carrying identity across an inherently stateless HTTP protocol — with different engineering trade-offs[cite: 1, 2]. Session tokens are centralized and easily revoked but require shared state[cite: 1, 2]; JWTs scale effortlessly across microservices and OutSystems applications but trade away effortless server-side revocation[cite: 1, 2]. Combining short-lived JWT access tokens with a robust refresh strategy gives you the best of both worlds: scalability, strong security, and fine-grained access control[cite: 1, 2].
